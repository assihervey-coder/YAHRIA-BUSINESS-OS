16. INVARIANTS
INV-001 — Tenant Isolation

Aucune donnée d'un tenant ne peut être accessible par un autre tenant.

INV-002 — Authorization

Toute opération protégée doit être autorisée.

INV-003 — Policy Enforcement

Toute opération sensible doit passer par le Policy Engine.

INV-004 — Financial Integrity

Tout mouvement financier doit être traçable.

INV-005 — Accounting Integrity

Les écritures comptables doivent respecter débit = crédit.

INV-006 — Idempotency

Les opérations financières critiques doivent être idempotentes.

INV-007 — Event Immutability

Un événement publié ne peut pas être modifié.

INV-008 — Evidence

Toute décision IA ayant un impact métier significatif doit produire une preuve exploitable.

INV-009 — Human Oversight

Les actions dépassant les seuils de risque ou d'autorisation nécessitent une validation humaine.

INV-010 — Agent Least Privilege

Un agent possède uniquement les permissions nécessaires à sa fonction.

INV-011 — Country Isolation

Les règles nationales sont encapsulées dans les Country Packs.

INV-012 — Sector Isolation

Les extensions sectorielles ne doivent pas contaminer le Core.

INV-013 — Versioning

Les contrats publics sont versionnés.

INV-014 — Auditability

Toute action critique est auditable.

INV-015 — Explainability

Les décisions IA critiques doivent être explicables.

La prochaine étape devrait être particulièrement importante : FILE_GENERATION_MANIFEST.md.

C'est lui qui transformera le manifeste d'implémentation en une liste déterministe fichier par fichier : chemin exact, type de fichier, bounded context, responsabilité, dépendances autorisées, classes/fonctions attendues, contrats consommés, invariants applicables et tests associés. C'est à ce niveau que nous pourrons réellement préparer le codage autonome de YAHRIA BUSINESS OS V1 sans dérive architecturale.
